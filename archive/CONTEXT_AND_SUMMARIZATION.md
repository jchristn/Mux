# Context, Summarization, and Universal Prompt Management

**Status:** Delivered (all six phases) · **Target release:** 0.12.3 · **Owner:** _unassigned_ · **Last updated:** 2026-09-16

This plan covers three pieces of work that turned out to be the same piece of work wearing three hats. The first is the visible complaint: when a surface loads a large file into the model's context it truncates the tail, so the interesting code at line 600 simply disappears. The second is a request that sounds unrelated but shares a root cause — every prompt the model ever reads should be something the user can see and edit, not a string buried in a `.cs` file. The third is a correctness sweep prompted by a real bug: clicking a row in the web dashboard's **Prompts** list opens the **Edit model pricing** dialog. All three come back to the same principle — the words and content mux feeds a model should be legible, editable, and wired to the thing the user thinks they clicked.

The work spans the whole product: the core engine, the `mux serve` REST server, the web dashboard, the terminal UI, the desktop app, the VS Code extension, the test suites, and the documentation. It ships as a patch on the 0.12 line (**0.12.3**) rather than opening a new minor.

## How to use this document

Every actionable item is a checkbox. A developer picks up a phase, works top to bottom, and checks items as they land — the checkbox state _is_ the progress tracker, so keep it current in the same commit that does the work. Phases are ordered by dependency: the prompt foundation in Phase 1 is what the surface work in Phases 2–4 consumes, and the large-file feature in Phase 5 leans on the same resolver and settings plumbing. Each phase closes with a **Definition of Done** that must be true before the next phase is considered unblocked.

The prose in each section explains _why_ a task exists and where the code lives, because a checklist with no reasoning ages badly the moment someone refactors the file it points at. When a file path or symbol here disagrees with the tree, trust the tree and update this document.

## Grounding: how things work today

Before the plan, the lay of the land, because several tasks below only make sense against the current shape.

**Large files are handled differently on each surface, and neither way is good.** The VS Code extension front-loads editor context into the user's turn: `collectContext()` in `src/Mux.VSCode/src/context/providers.ts` reads the whole active file, and `composePrompt()` in `src/Mux.VSCode/src/context/composePrompt.ts` then hard-slices every context item at 8000 characters with a `… [truncated N characters]` marker. The terminal UI and desktop app do the opposite — they attach nothing eagerly and rely entirely on the agent calling the `read_file` tool. That tool (`src/Mux.Core/Tools/Tools/ReadFileTool.cs`) refuses any file over 1 MB outright with a `file_too_large` error (`ToolSafetyLimits.MaxReadFileBytes`), so the "truncation" on those surfaces is really a flat refusal that forces the model to page with `offset`/`limit`. The extension's LSP outline provider already has each symbol's full `range` in hand but emits only the start line, so the cheapest possible "map with line ranges" is one edit away from existing.

**Most of the prompts the model reads are invisible to the user.** `PromptProfile` (`src/Mux.Core/Models/PromptProfile.cs`) carries three editable fields — `SystemPrompt`, `ToolsDisabledPrompt`, `CompactionPrompt` — persisted to `~/.mux/prompts.json`. The web projection `PromptProfileDto` exposes only `SystemPrompt`, so even the compaction prompt that already exists in the model cannot be edited from the dashboard. Everything else is a hardcoded string: the task-planning guidance block and defaults in `src/Mux.Core/Settings/Defaults.cs`; the compaction _user_ framing (`"Compact this older conversation history:\n\n"`) duplicated in both `ConversationCompactor.cs` and `AgentLoop.cs`; the synthetic-summary prefix duplicated in the same two files; the title-generation prompts in `src/Mux.Desktop.Core/Conversation/AgentLoopTurnRunner.cs`; roughly fifteen tool `Description` strings under `src/Mux.Core/Tools/Tools/`; the skills and MCP prompt-section lead-ins (`SkillRuntime.BuildPromptSection`, `McpTemplateBinder.BuildMcpSection`); the probe prompt; and eight subagent seed personas in `src/Mux.Core/Subagents/DefaultSubagents.cs`. Prompts are stored as plain JSON files — there is no database in this path, so the "type of use" the user asked about is a property on a prompt object, not a database column.

**The web dashboard's Prompts rows are wired to the pricing editor.** `src/Mux.Server/DashboardPage.cs` builds one large inline `<script>`. The Prompts section defines `openPr` / `prFields` / `delPr`, and the Pricing section — later in the same scope — defines functions with the _same three names_. JavaScript hoisting means the pricing definitions win everywhere, so the Prompts grid's `row:` handler calls the pricing `openPr` and opens "Edit model pricing." Every other section escaped this only by luck of using a unique name prefix (`Ep`, `Mcp`, `Sa`, …); Prompts and Pricing are the one collision. The fix is mechanical, but it is a symptom of a structural fragility — a single flat script scope where isolation depends on nobody reusing a name — so the plan pairs the fix with a wiring audit across every surface.

## Goals and non-goals

The goals are concrete. Replace truncation with a structural map (and optional summary) for large files, on every surface, with the mode under user control. Make every string the model ever reads appear in a **Prompts** view somewhere in each product, editable, with a sensible default and a reset. Fix the Prompts/Pricing cross-wiring and prove, with tests, that every management action on every surface opens the editor it claims to. Ship it as 0.12.3 with documentation and regression coverage.

A few things are explicitly out of scope so the plan stays finishable. This is not a move to a database-backed prompt store — mux's prompts stay file-based JSON, consistent with the rest of its single-user local configuration, and the multi-tenant, RBAC, and provider-matrix requirements in `BACKEND_ARCHITECTURE.md` are noted as documented single-user deviations rather than adopted. It is not a rewrite of the web dashboard into the React/Vite structure the frontend requirements describe; the dashboard is a self-contained single page, and this plan improves it in place. And it does not attempt semantic chunking or embeddings for the file map — the map is structural and the summary is a plain map-reduce, because ground-truth line ranges plus the agent's own `read_file`/`grep` beat a fuzzy vector recall for this job.

## Design

### The prompt catalog and the `PromptKind` taxonomy

The organizing idea is a single catalog of every model-facing prompt, where each entry knows what it is for. Persona prompts — the system prompt and its tools-disabled variant — stay inside the existing switchable `PromptProfile`, because users genuinely want more than one persona and want to swap the active one. Everything else becomes an **operational** entry in a global catalog that is independent of which profile is active, because nobody wants three copies of their title-generation prompt just because they keep three personas. Both halves share one `PromptKind` taxonomy so that a Prompts view can group and label the whole set uniformly, and so the "type of use" is a first-class property rather than an inference from which field a string happens to live in.

The catalog is defined in code (`src/Mux.Core/Prompting/PromptCatalog.cs`, new) so that defaults always exist even when no file is present — this is what satisfies "pre-populated with sensible defaults out of the box" without shipping a giant seed file. User overrides are additive: profile persona prompts continue to live in `prompts.json` under the profile; operational overrides live in a new, forward-tolerant `operational` section of the same file (a `key → override string` map), so a missing key means "use the coded default" and deleting a key is the reset. A single resolver (`src/Mux.Core/Prompting/PromptResolver.cs`, new — or an extension of the existing `SystemPromptResolver`) becomes the one place any subsystem asks for a prompt by key, which also lets us delete the duplicated compaction-framing and synthetic-summary-prefix literals by pointing both call sites at the same catalog entry.

The taxonomy below is the initial set. Because the chosen scope is _everything the model reads_, it includes tool descriptions and the structured tool-result payloads, with the understanding that the latter are structured strings and their editability is a power-user affordance, not a headline feature. Guardrails matter here: a mangled `read_file` description can quietly degrade tool use, so every entry ships with its default, a one-click reset, and validation that required placeholders (like `{WorkingDirectory}`) survive an edit.

| Kind | Scope | Example keys | Source today |
|---|---|---|---|
| `SystemPersona` | Profile | `system`, `tools-disabled` | `PromptProfile.SystemPrompt` / `Defaults.SystemPrompt` |
| `Compaction` | Global | `compaction.system`, `compaction.user`, `compaction.summary-prefix` | `Defaults.CompactionSystemPrompt`, duplicated literals in `ConversationCompactor.cs` / `AgentLoop.cs` |
| `TaskPlanning` | Global | `task-planning.guidance` | `Defaults.TaskPlanningGuidance` |
| `TitleGeneration` | Global | `title.system`, `title.user` | `AgentLoopTurnRunner.cs` (hardcoded) |
| `ToolSection` | Global | `section.skills`, `section.mcp` | `SkillRuntime.BuildPromptSection`, `McpTemplateBinder.BuildMcpSection` |
| `ToolDescription` | Global | `tool.read_file`, `tool.grep`, `tool.plan_tasks`, `tool.spawn_subagent`, … | each tool's `Description` |
| `ToolResult` | Global | `result.tool_call_denied`, `result.tool_execution_error`, `result.unknown_tool`, `digest.role-labels` | `AgentLoop.cs` status payloads |
| `Diagnostics` | Global | `probe.system`, `probe.user` | `ProbeCommand.cs` |
| `FileContext` | Global | `file.map`, `file.summary.map`, `file.summary.reduce` | new (see below) |
| `SubagentPersona` | External (cross-linked) | `subagent.<name>` | `subagents.json` (existing Subagents manager) |

Subagent personas are the one category that keeps its own home. They already persist to `subagents.json` and already have a dedicated manager on every surface, so duplicating them into the prompt store would create two sources of truth. Instead, the Prompts views list them read-through with a deep link to the Subagents editor — present in the inventory, edited where they already live.

### Large-file context: map, summarize, or truncate

The large-file feature is a Core service, `FileContextBuilder` (`src/Mux.Core/Context/FileContextBuilder.cs`, new), that turns a file plus a mode into a context block. The mode is user-selectable with three values and a size gate. Small files inline whole, exactly as today. Large files follow the configured `LargeFileMode`: **Map** (the default) emits a structural outline with line ranges plus the first N lines; **Summarize** runs an iterative map-reduce and emits a dense summary that still carries line-range pointers; **Truncate** preserves today's head-slice for anyone who wants it. Map is the default because it is instant, free, and lossless — it tells the model "the auth API is in lines 400–508" and lets the agent pull exactly that range with `read_file(offset, limit)`, which is ground truth rather than a summary that can drop a detail.

The map is built structurally, and the builder resolves an outline through a small provider abstraction (`IFileOutlineProvider`) so the source of structure is swappable. Where a caller can supply a real outline — the VS Code extension has one from the language server — the builder consumes it, and the one-line fix to emit `symbol.range.end.line` alongside the start turns the existing outline into true line ranges. Where no outline is available (the Core path, the TUI, the desktop, and the agent's own `read_file`), the first cut ships a single generic provider rather than a library of per-language parsers. It reads the file as a Markdown-style document — Markdown and heading-bearing formats parse by their headings; everything else falls back to blank-line-delimited and brace/indent-delimited blocks — and emits a line-anchored table of contents. This is deliberately coarse: it beats truncation because it is line-anchored, and it will never be as precise as a language server, but chasing per-language precision in Core is speculative work we are choosing not to do yet. The `IFileOutlineProvider` seam is the whole point of naming it — a C# or TypeScript or Python parser can be registered later without touching the builder or any surface, if and when the generic map proves too blunt in practice. The summary path reuses machinery that already exists for conversation compaction: the sidecar-endpoint pattern (`AgentLoop.CreateSidecarEndpoint` — tools off, temperature 0, non-streaming, capped output) and `RunSidecarPromptAsync`. What is new is the loop — chunk the file into line-budgeted windows, take notes on each with the `file.summary.map` prompt, then reduce the notes with `file.summary.reduce` into the final map — and a cache, because summarizing on every turn would be an unacceptable latency tax. The cache is loose files, one artifact per entry under `~/.mux/cache/file-summaries/`, content-addressed by `(path, contentHash, mode, model)` and invalidated automatically when the file's hash changes. Loose files were chosen over a SQLite table on purpose: there is no schema to migrate, a corrupt entry costs one file rather than a shared database, and eviction is a directory sweep. Because it is a cache and nothing more, it expires — entries older than a retention window are deleted by a periodic cleanup pass, and the window is a tunable setting (`SummaryCacheRetentionDays`, default 7) surfaced on every product surface's settings, so a user who wants a longer or shorter memory sets it once and every surface honors it. Cleanup runs opportunistically (on server start and on a low-frequency timer) rather than as a foreground cost on the request path.

Because the chosen reach is whole-product, the feature also changes the agent's own path, not just the eager-injection one. When `read_file` meets a file over the byte threshold, instead of a flat `file_too_large` refusal it returns a structural map and a note that the agent can request a summary or page with `offset`/`limit`. This is gated by the same `LargeFileMode` setting so the behavior is one concept the user controls in one place, and it degrades safely: the old refusal remains available as the `Truncate`/`Refuse` setting for anyone who wants the strict cap. The server exposes a route (`POST /v1.0/api/context/file`) so the VS Code extension — a thin client that cannot run the summarizer itself — can ask the server to build a map or summary and receive the cached result. The extension then stops hard-slicing the active file and instead inlines small files, maps or summarizes large ones, and keeps truncation only as the explicit fallback mode.

The behavior is configuration, so it lives in settings: a `context` group with `LargeFileMode` (`map` | `summarize` | `truncate`), `InlineThresholdBytes`, `SummaryChunkLines`, `SummaryCacheEnabled`, and `SummaryCacheRetentionDays` (default 7), surfaced on the Settings page of every surface and validated/clamped on write per the settings conventions.

### The correctness pass on surface wiring

The Prompts/Pricing collision is a one-file fix — rename the pricing trio to `openPrice` / `priceFields` / `delPrice` and update its `wireTable`/`on` call sites — but shipping only the fix would miss the point. The real deliverable is a guarantee, backed by tests, that every management action on every surface opens the editor it names. That means enumerating, per surface, each clickable management affordance (row click, context-menu edit/delete, add button) and its intended target, then asserting the wiring matches. The audit already has a head start: the survey found the web dashboard is the only surface with a genuine cross-wiring, because the TUI, desktop, and VS Code each bind strongly-typed, per-section handlers that the type system or explicit command IDs keep honest. The tests still get written for all four, because "correct today" and "stays correct" are different claims, and a regression test is what makes the second one true.

## Testing strategy

The test work is threaded through the phases rather than saved for the end, because a suite written next to the code it covers is the one that actually runs. All of it lives in `Test.Shared` as Touchstone descriptors so the console runner, xUnit, and NUnit adapters pick it up for free, and every in-process server binds and is targeted at `127.0.0.1` per the backend-test conventions. The new suites are `PromptCatalogSuite` (defaults, override round-trip, reset, resolver precedence, de-duplication), the server route additions for the catalog and the fixed profile DTO, `SurfaceWiringSuite` (the correctness matrix), and `FileContextSuite` (map, summarize, cache, agent large-file path, truncate fallback). Existing suites get extended rather than replaced: `MuxServerRouteSuite` gains catalog and file-context assertions, and the VS Code extension's unit tests gain the per-node-kind command binding check.

Regression coverage is the part that earns its keep here. The Prompts/Pricing collision existed because nothing failed when a name was reused; the `SurfaceWiringSuite` closes that gap by asserting the mapping from affordance to editor, so reintroducing the bug turns a test red. The file-context suite guards the more subtle regression — that a change to chunking or caching silently starts re-summarizing every turn — by asserting a cache hit on an unchanged file.

## Risks and open questions

The largest risk is the blast radius of routing every model-facing string through one resolver. It is the right refactor, but it touches the hot path of every turn, so Phase 1 ships behind its own suite and changes no behavior — only indirection — before any surface consumes it. The second risk is the agent-facing `read_file` change: turning a refusal into a map alters what the model sees on large files, and a model that previously learned to page with `offset`/`limit` should still be able to, so the map explicitly tells it how. The summary cache introduces a correctness question of its own — a stale summary is worse than none — which the content-hash key is designed to prevent, and the `FileContextSuite` verifies.

Two design forks that were open at planning time are now settled, and they are recorded here so nobody reopens them without cause. The summary cache is loose files under `~/.mux/cache/file-summaries/` with a tunable retention window (default seven days) and a periodic cleanup pass, not a SQLite table — queryability was judged not worth a migration for a disposable cache. The non-LSP outline ships as a single generic Markdown-oriented provider with no per-language parsers in the first cut; the `IFileOutlineProvider` seam exists precisely so a language-specific parser can be added later without disturbing the builder or any surface, and that is the intended path if the generic map reads too bluntly once it is in real use.
